# PySM System Updater v2.2026.08.30

## Назначение

Скрипт обновляет установленный PySM через portable Git. Он не скачивает ZIP-архив и не распаковывает файлы поверх рабочей папки. Вместо этого updater получает состояние ветки GitHub, показывает план обновления, анализирует локальные изменения и применяет обновление Git-командами.

Главная цель такого подхода - обновлять файлы приложения, но не трогать рабочие данные пользователя: настройки, логи, модели, кеши, результаты обработки и другие локальные файлы.

## Расположение Git

По умолчанию используется portable Git рядом с установкой PySM:

```text
<base>\repos\PySM
<base>\ps_env\git\cmd\git.exe
```

Например:

```text
D:\PySM3_Codex\repos\PySM
D:\PySM3_Codex\ps_env\git\cmd\git.exe
```

Если общий путь `<base>` на другом компьютере отличается, это нормально. Важно только относительное расположение папок `repos\PySM` и `ps_env\git`.

Если Git лежит в другом месте, укажите параметр `git_path`.

## Куда пишется лог

Краткий ход работы выводится в консоль PySM. Полный текстовый лог и JSON-отчет сохраняются в:

```text
<PySM>\_OUTPUT\pysm_updater\update_YYYYMMDD_HHMMSS.log
<PySM>\_OUTPUT\pysm_updater\update_YYYYMMDD_HHMMSS.json
```

Текстовый лог предназначен для чтения человеком. JSON-отчет нужен для диагностики и автоматической обработки: в нем сохраняются выбранные параметры, remote, план обновления, локальное состояние и итог.

В консоли PySM локальное состояние выводится HTML-блоками с иконками из `pysm_lib.pysm_icons`. Текстовый `.log` остается обычным plain text, чтобы его было удобно прикладывать к отчетам и анализировать поиском.

В конце работы updater также выводит кликабельный HTML-блок со ссылками на папку отчетов, полный `.log` и `.json`-отчет. Блок строится через `ResourceNode` и `StandardTreeBuilder`, как в workflow-скриптах PySM.

## Что такое origin и remote

`remote` - это имя удаленного репозитория в Git. Обычно главный удаленный репозиторий называется `origin`.

`origin` хранится в `.git/config` и обычно указывает на GitHub-репозиторий PySM:

```text
https://github.com/ExMent-70/PySM.git
```

Если `origin` настроен, updater использует его URL. Если `origin` не настроен, updater использует параметр `remote_url` и выполняет `fetch` напрямую по URL. При этом он не записывает новый remote в `.git/config`, а только обновляет локальную ссылку вида:

```text
refs/remotes/origin/main
```

То есть параметр `remote_url` - это безопасный запасной вариант для получения данных с GitHub без изменения настроек Git checkout.

## Общая логика обновления

1. Updater определяет папку установки PySM.
2. Находит portable `git.exe`.
3. Проверяет, что папка PySM является Git checkout.
4. Определяет remote и URL репозитория.
5. Проверяет, что remote указывает на ожидаемый репозиторий PySM.
6. При реальном запуске добавляет локальные Git-исключения в `.git/info/exclude`; в режиме `update_mode=plan` только сообщает, если они требуют обновления.
7. Выполняет `git fetch --progress --prune` и показывает прогресс загрузки в progress-bar PySM.
8. Сравнивает текущий `HEAD` с remote-веткой, например `origin/main`.
9. Показывает план обновления: текущий commit, remote commit, новые коммиты и измененные файлы.
10. Всегда анализирует локальное состояние рабочей папки, даже если новых commit нет.
11. В режиме `update_mode=plan` завершает работу без изменения файлов.
12. Восстанавливает отсутствующие файлы приложения из Git. Для локально удаленных настроек и коллекций после обновления остается версия GitHub.
13. Если новых commit нет, но включен `repair_git_state`, синхронизирует Git-состояние без перезаписи рабочих файлов.
14. При обычном обновлении сохраняет локальные копии `config.toml` и файлов из `script_collections`, а конфликтующие изменения кода блокирует.
15. Перед применением создает ZIP-бэкап, если включен `create_backup`.
16. Перед `force` дополнительно создает обязательный архив всех существующих tracked-файлов.
17. Применяет выбранный режим обновления.
18. Сравнивает хеш `requirements.txt` до и после успешного обновления.
19. Если зависимости изменились в portable-установке, создает marker для внешнего `start.bat`.
20. Пишет итог и пути к логам.

## Зависимости после обновления

Updater обновляет только исходный код PySM и **никогда не запускает** `pip`, `uv` или `py_install_req`. Поэтому он не может повредить активное окружение во время работы приложения.

После успешного обновления он сравнивает содержимое `requirements.txt`. Если файл не менялся, дополнительное действие не требуется. Если файл изменился и PySM установлен через `pysm-setup` в структуре `<portable>\repos\PySM`, updater создает marker:

```text
<portable>\ps_env\state\pending-pysm-dependency-sync.json
```

При следующем запуске внешнего `start.bat` PySM не будет запущен сразу: launcher предложит выполнить синхронизацию. Команда `pysm-setup sync-pysm-deps` создаст отдельный candidate venv, запустит штатный `py_install_req` из checkout PySM, проверит пакеты и CUDA, и заменит `envs\pysm` только после успеха. При отказе от синхронизации launcher вернет пользователя в главное меню, а не будет запускать PySM с потенциально устаревшими зависимостями.

В development checkout без portable `ps_env\state` marker намеренно не создается: там окружением управляет разработчик.

## Почему анализ выполняется даже без обновлений

Git может сказать, что новых commit нет, потому что локальный `HEAD` уже равен `origin/main`. Но рабочая папка при этом все равно может содержать локально измененные файлы.

Например:

* `config.toml` меняется при работе PySM;
* файлы `*.context.json` меняются при работе с коллекциями;
* файлы updater могли быть вручную скопированы из другой папки;
* старый ZIP-updater мог заменить файлы на диске, но не обновить Git-индекс.

Поэтому updater после каждого `fetch` отдельно показывает локальное состояние. Это помогает понять, что именно отличается на диске, даже если обновлять уже нечего.

## Прогресс загрузки

Во время получения данных с GitHub updater запускает `git fetch` в потоковом режиме. Строки Git вроде `Counting objects`, `Compressing objects`, `Receiving objects` и `Resolving deltas` разбираются сразу, пока команда еще работает.

Если GitHub отдает большой файл или много файлов, в консоли PySM будет видно, что процесс не завис: текущая фаза и процент показываются в progress-bar. Сотни технических строк Git не выводятся в основную консоль PySM, но сохраняются в полном текстовом логе обновления и используются в сообщении об ошибке, если `fetch` завершится неудачно.

## Компактность консольного отчета

В основной консоли PySM updater показывает сводку и короткий предпросмотр длинных списков: новые commit, измененные файлы, локальные правки, untracked-файлы и конфликты. Количество строк предпросмотра задается параметром `console_preview_limit`.

Полные списки сохраняются в `update_*.log`, а машинно-читаемые данные - в `update_*.json`. Это позволяет быстро понять результат в интерфейсе PySM и при необходимости открыть полный отчет для диагностики.

## Категории локального состояния

Updater делит локальные изменения на несколько групп.

Git внутри использует короткие технические статусы, например `M` для modified и `??` для untracked. Updater не показывает эти коды напрямую в пользовательском логе. Вместо них используются расшифровки:

* `Изменен локально` - tracked-файл отличается в рабочей папке;
* `Новый файл вне Git` - файл существует на диске, но не отслеживается Git;
* `Удален локально` - tracked-файл удален из рабочей папки;
* `Добавлен локально` - файл добавлен в индекс;
* `Переименован` - Git видит переименование;
* `Конфликт` - Git видит конфликтующее состояние.

### Файлы уже совпадают с remote

Это tracked-файлы, которые Git считает измененными, но их содержимое уже байт-в-байт совпадает с файлом из `origin/main`.

Такая ситуация часто появляется после старого обновления через ZIP: файл на диске уже новый, но Git еще считает `HEAD` старым.

В логе для этой группы дополнительно показывается диагностика:

```text
index=N, worktree=M
```

`index` означает, что отличие видно на уровне Git-индекса. `worktree` означает, что отличие видно на уровне рабочего файла. После `repair_git_state` updater выполняет `git reset --mixed origin/main`, переоформляет из Git-индекса только файлы из безопасной группы "уже совпадают с remote", а затем запускает `git update-index --refresh`.

### Локальные настройки и коллекции

`config.toml` и всё содержимое `script_collections/` относятся к пользовательскому состоянию PySM. Приложение и его коллекции меняют эти файлы при обычной работе, поэтому они не должны мешать обновлению программы.

Если такой файл одновременно изменен локально и в GitHub-обновлении, updater сохраняет локальную версию рядом с исходным файлом. Имя получает общий для одного запуска префикс:

```text
user_YYYYMMDD_HHMMSS_config.toml
user_YYYYMMDD_HHMMSS_Имя коллекции.pysmc
user_YYYYMMDD_HHMMSS_Имя коллекции.context.json
```

После обновления исходный путь занимает версия GitHub. В логе выводится заметное предупреждение и список созданных копий: сравните их с новыми файлами и вручную перенесите нужные настройки.

Копии `.pysmc` и `.context.json` сохраняют одинаковый префикс, поэтому образуют отдельную рабочую копию коллекции. Копия `config.toml` остается корректным TOML-файлом, но не становится активной конфигурацией PySM: приложение использует точное имя `config.toml`.

Если пользователь удалил файл из `config.toml` или `script_collections/`, копировать нечего. После обновления на исходном пути останется версия GitHub; это также будет показано в логе.

### Локальные изменения вне обновления

Это tracked-файлы, которые отличаются от `origin/main`, но не пересекаются с файлами текущего обновления.

Примеры: локальные рабочие правки кода или ресурсов, которые не затрагивает текущее обновление.

Обычное обновление не должно перезаписывать такие файлы.

### Отсутствующие файлы из репозитория

Это tracked-файлы, которые есть в `origin/main`, но удалены из рабочей папки. Например, пользователь случайно удалил файл темы оформления.

Такие файлы updater восстанавливает автоматически, даже если новых commit на GitHub нет. Для этого используется восстановление из Git-индекса:

```text
git reset -- <missing files>
git checkout-index -f -- <missing files>
git update-index --refresh
```

Этот режим не перезаписывает измененные локальные файлы. Он возвращает только файлы приложения, которых физически не хватает на диске.

### Локальные конфликты с обновлением

Это tracked-файлы вне `config.toml` и `script_collections/`, которые изменены локально и одновременно должны измениться в обновлении.

В обычном режиме updater останавливается, чтобы не потерять локальные правки. Такой конфликт нужно разобрать вручную или использовать `force`, если локальные правки точно не нужны.

### Untracked-файлы вне обновления

`Untracked` - это файлы, которые лежат в рабочей папке, но не находятся под контролем Git.

Git их не обновляет и не откатывает. Обычно это локальные данные, результаты работы, кеши, модели, временные файлы или новые пользовательские файлы.

### Untracked-файлы, мешающие обновлению

Это untracked-файлы, которые занимают путь, куда обновление должно добавить tracked-файл из GitHub.

В обычном режиме updater блокирует обновление, потому что Git не должен молча заменить такой файл.

## Локальные Git-исключения

Updater не меняет tracked `.gitignore` в репозитории. Вместо этого он дописывает правила в локальный файл:

```text
.git\info\exclude
```

Этот файл действует только на текущем компьютере и не попадает в репозиторий.

Добавляемые правила:

```text
_BIN/
_OUTPUT/
_backups/
huggingface_home/
**/_Cache/
**/_Embeddings/
*.log
```

Это уменьшает шум от runtime-файлов, моделей, кешей, логов и бэкапов.

## Обычный режим обновления

Обычный режим использует:

```text
git merge --ff-only origin/main
```

Это безопасный fast-forward. Перед ним updater сохраняет локальные копии настроек и коллекций, если они пересекаются с обновлением, а исходные пути обновляет версией GitHub. Он применяется только тогда, когда локальная история не расходится с GitHub и нет блокирующих конфликтов в коде или ресурсах приложения.

Если fast-forward невозможен, updater останавливается и пишет причину.

## Режимы plan и apply

Параметр `update_mode` одинаково работает в PySM и при прямом запуске из терминала:

* `plan` — получить данные, показать план и проанализировать локальное состояние без изменения файлов;
* `apply` — применить обновление после всех проверок.

Безопасное значение по умолчанию — `plan`. Из терминала режим задается так же явно: `--update_mode plan` или `--update_mode apply`.

В существующих экземплярах скрипта старый параметр `dry_run` больше не используется. После обновления паспорта откройте параметры экземпляра и выберите `update_mode=apply`, если требуется реальное обновление.

Файлы не меняются, бэкап не создается, Git-состояние не чинится, отсутствующие файлы не восстанавливаются, `.git/info/exclude` не дописывается.

Этот режим удобен перед реальным обновлением или перед включением `repair_git_state` / `force`.

## Repair Git State

`repair_git_state` нужен для перехода после старого ZIP-обновления.

Старый updater мог распаковать новые файлы поверх старой рабочей папки. В результате содержимое файлов уже соответствует GitHub, но Git все еще считает их локально измененными.

Если режим `plan` показывает, что блокирующих конфликтов нет, можно включить `repair_git_state`. Этот режим предназначен для восстановления Git-состояния после старого ZIP-обновления, когда рабочие файлы уже совпадают с remote. Он не используется как обычный способ скачать новые файлы из GitHub.

Тогда updater выполняет:

```text
git reset --mixed origin/main
git checkout-index -f -- <already-remote files>
git update-index --refresh
```

Что меняется:

* `HEAD` синхронизируется с `origin/main`;
* Git-индекс синхронизируется с `origin/main`;
* рабочие файлы, которые уже совпадают с remote, могут быть переоформлены из Git-индекса, чтобы Git применил свои правила окончаний строк и фильтров.

Что сохраняется:

* локальные изменения вне обновления;
* `config.toml`;
* контекстные файлы коллекций;
* untracked-файлы и папки.

Если новых commit нет, `repair_git_state` все равно имеет смысл: он убирает ложные `M` у tracked-файлов, которые уже совпадают с remote, но по-прежнему числятся измененными в Git-состоянии после старого ZIP-обновления.

Если на GitHub есть новые commit и часть файлов обновления еще не находится в рабочей папке, updater блокирует `repair_git_state` и предлагает выполнить обычное обновление без этого режима.

## Force

`force` нужен только тогда, когда требуется принудительно вернуть tracked-файлы к состоянию GitHub.

`force` не сбрасывает локальные commit. Если локальная ветка содержит commit, которых нет в remote, updater останавливается и просит сначала сохранить, отправить или вручную разобрать локальную историю.

Перед этой командой updater **всегда** создает отдельный архив текущих tracked-файлов системы:

```text
<PySM>\_backups\pysm_force_system_YYYYMMDD_HHMMSS.zip
```

В этот архив не входят untracked-файлы, логи, модели и результаты работы. Он создается даже при `create_backup=false`, потому что `force` заменяет tracked-файлы без возможности отмены.

После этого выполняется:

```text
git reset --hard origin/main
```

Что меняется:

* все tracked-файлы перезаписываются версией из `origin/main`;
* локальные tracked-изменения теряются;
* `config.toml`, если он tracked и изменен локально, тоже будет перезаписан;
* вручную замененные файлы updater тоже будут перезаписаны.

Что не меняется:

* untracked-файлы не удаляются;
* untracked-папки не удаляются;
* `_BIN`, `_OUTPUT`, `_backups`, `huggingface_home`, `_Cache`, `_Embeddings` не очищаются этим режимом.

Полного режима `force_clean`, который удаляет все лишнее и приводит рабочую папку к абсолютно чистому состоянию remote, в updater нет. Это сделано намеренно, чтобы не удалить пользовательские данные, модели, логи и результаты работы.

## Бэкап

Перед реальным обновлением updater создает ZIP-бэкап в:

```text
<PySM>\_backups\
```

Из бэкапа исключаются тяжелые и runtime-папки:

```text
.git
.codex
__pycache__
_backups
_BIN
_Cache
_Embeddings
_OUTPUT
huggingface_home
```

Если в исключенных папках остались tracked-файлы старых версий и обновление будет их менять или удалять, updater добавляет такие файлы в ZIP-бэкап отдельно. Остальные модели, кеши, TensorRT-файлы и другие тяжелые runtime-данные по-прежнему не архивируются.

В логе показывается количество файлов и прогресс упаковки. Это не интерактивный progress-bar, а устойчивые строки лога, которые остаются полезными после завершения скрипта.

Если обычный бэкап не нужен, выключите `create_backup`. Для обычной эксплуатации это не рекомендуется.

## Безопасность

Updater блокирует работу, если:

* папка PySM не является Git checkout;
* remote не указывает на ожидаемый репозиторий;
* локальная и удаленная истории разошлись;
* локальные изменения пересекаются с файлами обновления;
* untracked-файл мешает добавить файл из обновления;
* fast-forward невозможен.

Проверка remote по умолчанию ожидает строку:

```text
github.com/ExMent-70/PySM
```

Если нужно обновляться из другого доверенного репозитория, можно изменить `expected_remote_contains` в формате `host/owner/repo` или включить `allow_untrusted_remote`. Делать это стоит только осознанно.

## Основные параметры

* `update_mode` - режим `plan` для просмотра или `apply` для применения обновления. По умолчанию `plan`.
* `remote` - имя remote, по умолчанию `origin`.
* `remote_url` - URL GitHub-репозитория, если remote не настроен.
* `branch` - ветка обновления, по умолчанию `main`.
* `git_path` - явный путь к `git.exe`.
* `repair_git_state` - синхронизировать `HEAD` и индекс с remote без перезаписи рабочих файлов.
* `force` - принудительно заменить tracked-файлы версией из remote через `git reset --hard`.
* `create_backup` - создавать обычный ZIP-бэкап перед обновлением. По умолчанию включен; на обязательный архив tracked-файлов перед `force` не влияет.
* `show_stat` - сохранить `git diff --stat` в полном логе и показать уведомление в консоли.
* `expected_remote_contains` - ожидаемый репозиторий remote в формате `host/owner/repo`.
* `allow_untrusted_remote` - разрешить remote, который не прошел проверку.
* `max_commits` - максимум коммитов, получаемых для отчета.
* `max_files` - максимум файлов и записей, сохраняемых в полном отчете для длинных списков.
* `console_preview_limit` - максимум строк предпросмотра для длинных списков в консоли PySM.

## Рекомендуемый порядок действий

Для обычной проверки:

```text
update_mode = "plan"
repair_git_state = false
force = false
```

Если после старого ZIP-обновления много файлов в группе "Файлы уже совпадают с remote" и нет блокирующих конфликтов:

```text
update_mode = "apply"
repair_git_state = true
force = false
```

Если нужно принудительно вернуть tracked-файлы к GitHub и локальные tracked-правки не нужны:

```text
update_mode = "apply"
repair_git_state = false
force = true
```

После успешного обновления перезапустите PySM.
