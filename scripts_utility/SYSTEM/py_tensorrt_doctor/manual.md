# Диагностика TensorRT

## Назначение

Скрипт независимо проверяет два способа использования NVIDIA TensorRT:

- прямой Python API через пакет `tensorrt`;
- провайдер `TensorrtExecutionProvider` в ONNX Runtime.

Такое разделение важно: ONNX Runtime может поставляться с нативным провайдером TensorRT даже тогда, когда команда `import tensorrt` в текущем Python недоступна.

Используйте скрипт:

- после установки или обновления TensorRT либо ONNX Runtime GPU;
- если приложение не может включить `TensorrtExecutionProvider`;
- если сборка TensorRT-движка завершается ошибкой;
- для сравнения прямого API и интеграции ONNX Runtime.

## Что проверяется

1. **Окружение Python** — версия и путь текущего интерпретатора.
2. **Прямой API TensorRT** — импорт пакета, версия и создание логгера.
3. **ONNX Runtime** — версия и список зарегистрированных провайдеров; отдельно отмечаются TensorRT и CUDA.
4. **Сборка движка** — если прямой API доступен, в памяти создаётся минимальная сеть и сериализуется тестовый движок.

Отсутствие прямого Python API не останавливает проверку ONNX Runtime. Отсутствие ONNX Runtime не мешает проверить прямой API.

Обычный способ — запустить скрипт из PySM. В этом режиме статусы оформляются тематическими значками из `pysm_icons.py`.

Из командной строки:

```powershell
D:\PySM3_Codex\envs\pysm\python.exe scripts_utility/SYSTEM/py_tensorrt_doctor/run_py_tensorrt_doctor.py
```

Справка:


## Как читать отчёт

- **Успех** — API инициализирован или провайдер зарегистрирован.
- **Предупреждение** — один сценарий недоступен, но другой может работать.
- **Ошибка** — найденный компонент не загрузился или минимальный движок не собрался.
- **Информация** — пояснение без оценки работоспособности.

Регистрация `TensorrtExecutionProvider` означает, что текущая сборка ONNX Runtime знает этот провайдер. Она не доказывает, что конкретная модель полностью поддерживается TensorRT или что каждый её узел будет выполнен через TensorRT. Окончательную проверку выполняйте на рабочей модели и с теми же параметрами провайдера, которые использует приложение.

## Типичные результаты

### Провайдер TensorRT есть, а пакет `tensorrt` не импортируется

Это допустимый вариант для приложения, использующего TensorRT только через ONNX Runtime. Для разработки через прямой Python API потребуется отдельная установка совместимого пакета `tensorrt`.

### Прямой API работает, а провайдера ONNX Runtime нет

Проверьте, что установлена GPU-сборка ONNX Runtime с поддержкой TensorRT и что её нативные библиотеки совместимы с установленным стеком CUDA/TensorRT.

### Есть TensorRT-провайдер, но нет CUDA-провайдера

Неподдерживаемые TensorRT узлы не смогут перейти на GPU-резерв через `CUDAExecutionProvider`. Возможен переход на CPU, что влияет на скорость и иногда на доступность модели.

### Минимальный движок не собирается

Технические сведения обычно указывают на несовместимость библиотек, ошибку драйвера или недостаток ресурсов GPU. Сравните версии и состояние системы через `py_gpu_doctor`.

## Требования и ограничения

- Для прямого API нужен пакет `tensorrt`.
- Для проверки провайдеров нужен пакет `onnxruntime` или `onnxruntime-gpu` соответствующей сборки.
- Минимальный движок создаётся только в памяти; скрипт не сохраняет `.engine` и не изменяет кеши приложения.
- Проверка не запускает пользовательские модели и не изменяет пользовательские данные.
