# План объединения `photo_selection` и `photo_selection_apply`

## Цель

Создать единый скрипт отбора фотографий, который закрывает весь этап подготовки данных для верстки альбома:

1. импорт и ручное редактирование выбора учеников;
2. сохранение `photo_selection.json`;
3. проверка выбранных фотографий по AI-анализу и физическим файлам;
4. копирование выбранных файлов в целевые папки;
5. создание `photo_assignments.json`;
6. контроль готовности к верстке.

Текущие источники функционала:

- `scripts/Workflow2/Tools/photo_selection`
- `scripts/Workflow2/FaceAnalysis/photo_selection_apply`

Целевой пользовательский результат: один скрипт, одно окно, один `script_passport.json`, одно руководство.

## Целевая папка

Основным объединенным скриптом становится:

```text
scripts/Workflow2/Tools/photo_selection/
```

Причина: итоговый инструмент относится к этапу workflow “отбор фотографий и подготовка данных”, а не только к анализу лиц.

`photo_selection_apply` на первом этапе желательно оставить как совместимую тонкую оболочку, чтобы не сломать существующие workflow-наборы. После реальных прогонов и стабилизации объединенного скрипта оболочку можно будет удалить из workflow.

## Основные файлы данных

### `photo_selection.json`

Рабочий файл выбора пользователя. Редактируется импортом, ручным вводом и исправлениями из интерфейса.

```json
{
  "schema_version": 1,
  "list_id": "HHC8",
  "session_name": "TEST_2027_2",
  "photo_session": "SCHOOL",
  "students": {
    "HHC8-S024": {
      "selected_numbers": ["888177", "889214"],
      "responded": true,
      "source": "ai_json"
    }
  }
}
```

### `photo_assignments.json`

Производный файл для генератора альбома. Не редактируется вручную. Создается из:

- `photo_selection.json`;
- файла класса `*.list`;
- `info_faces.json`;
- `matches_portrait_to_group.json`, если нужен;
- физических файлов в `source_dir`;
- физических файлов в `dest_dir`.

```json
{
  "schema_version": 1,
  "list_id": "HHC8",
  "assignments": {
    "HHC8-S024": ["888177", "889214"]
  }
}
```

## Главное правило актуальности

Любое изменение выбора ученика делает `photo_assignments.json` неактуальным.

К таким изменениям относятся:

- импорт общей CSV;
- импорт персональных CSV;
- импорт AI JSON;
- ручное редактирование номеров;
- очистка выбора;
- добавление номера из вкладки `По ученикам и локациям`;
- изменение номера из вкладки `По ученикам и локациям`.

После изменения выбора скрипт должен:

1. обновить внутреннюю модель выбора;
2. пометить `selection_dirty`;
3. пометить `assignments_dirty`;
4. сохранить или предложить сохранить `photo_selection.json`;
5. пересчитать вкладки назначения через worker `refresh`;
6. показать, что `photo_assignments.json` нужно пересоздать.

Готовность к верстке определяется только фактическим состоянием:

- `photo_assignments.json` существует;
- JSON читается;
- содержимое файла совпадает с текущим `assignment_payload`;
- для всех назначенных номеров есть `.jpg`, `.jpeg` или `.psd` в целевой папке;
- нет блокирующих ошибок.

Нельзя полагаться на внутренние флаги вида “файл был создан в текущем запуске”.

## Интерфейс

Окно должно содержать три вкладки.

### Вкладка 1. `Импорт`

Функции:

- импорт общей CSV;
- импорт персональных CSV;
- AI-промпт / JSON;
- ручное редактирование выбранных номеров;
- очистка выбора;
- сохранение `photo_selection.json`;
- вывод результата последней операции импорта;
- отображение данных выбранного ученика из `.list`.

Таблица:

```text
student_id | Фамилия Имя | Выбранные номера | Количество | Ответ | Источник
```

После сохранения или изменения выбора нужно запускать пересчет вкладок 2 и 3 через worker `refresh`.

### Вкладка 2. `По фотографиям`

Функции из текущего `photo_selection_apply`:

- список выбранных/назначенных кадров;
- источник выбора: клиент / фотограф;
- распознанные и назначенные ученики;
- физические файлы;
- предпросмотр JPG;
- контекстное меню:
  - открыть файл;
  - открыть папку с выделением файла.

### Вкладка 3. `По ученикам и локациям`

Функции:

- группировка:
  - ученик;
  - локация;
  - фото;
  - физические файлы;
- статус ученика: `выбрано локаций / всего локаций`;
- визуальное выделение отсутствующего выбора;
- HTML-отчет по выбранному ученику/локации;
- экспорт HTML;
- экспорт CSV.

Обязательное новое поведение:

- контекстное меню на ученике или локации:
  - `Изменить выбранные номера`;
  - `Добавить номер`;
  - `Очистить выбор ученика`;
- после редактирования:
  - обновить модель выбора;
  - сохранить или пометить dirty;
  - пересчитать назначения через worker `refresh`;
  - обновить вкладки 2 и 3;
  - показать, что `photo_assignments.json` нужно пересоздать.

## Панели кнопок

Используем две панели кнопок, каждая привязана к своей группе вкладок. Это утвержденное решение.

### Панель вкладки `Импорт`

Кнопки:

- `Импорт`
- `Изменить выбранные номера`
- `Очистить`
- `Сохранить выбор`

### Панель вкладок назначения

Кнопки:

- `Обновить список`
- `Копировать выбранные файлы`
- `Создать список`
- `Копировать и создать список`

Панели переключаются вместе с активной вкладкой. Это проще для оператора, чем один общий набор кнопок со сложной доступностью.

## Единое состояние окна

Создаем отдельный dataclass состояния. Это утвержденное решение.

Предлагаемая модель:

```python
@dataclass
class PhotoSelectionSessionState:
    selection_dirty: bool = False
    assignments_dirty: bool = False
    last_selection_saved_at: datetime | None = None
    last_assignments_saved_at: datetime | None = None
    build_result: BuildResult | None = None
    copy_summary: CopySummary | None = None
```

Назначение полей:

- `selection_dirty` — выбор изменен, но не сохранен в `photo_selection.json`;
- `assignments_dirty` — выбор или физические файлы изменились, `photo_assignments.json` нужно пересоздать;
- `last_selection_saved_at` — время последнего успешного сохранения `photo_selection.json`;
- `last_assignments_saved_at` — время последнего успешного создания `photo_assignments.json`;
- `build_result` — текущий результат анализа назначений;
- `copy_summary` — результат последнего копирования.

Нельзя плодить независимые GUI-флаги без привязки к этой модели состояния.

## Worker и фоновые операции

Используем worker `refresh`, который уже есть в `photo_selection_apply`. Это утвержденное решение.

Фоновые операции:

- `refresh` — пересканировать анализ, `source_dir`, `dest_dir` и пересчитать назначения;
- `copy` — скопировать выбранные файлы;
- `build` — создать `photo_assignments.json`;
- `copy_and_build` — скопировать, повторно пересканировать и создать `photo_assignments.json`.

Когда пользователь редактирует выбор:

1. обновляется модель `photo_selection`;
2. сохраняется или помечается `selection_dirty`;
3. запускается `refresh`;
4. результат `refresh` обновляет вкладки `По фотографиям` и `По ученикам и локациям`;
5. `photo_assignments.json` помечается неактуальным, пока пользователь не выполнит `Создать список` или `Копировать и создать список`.

Импорт CSV/JSON обычно можно оставить в GUI-потоке. Если на реальных данных появится заметная задержка, импорт можно будет вынести в отдельный worker позже.

## Правая HTML-панель

Правая панель общая для всего окна.

Режимы:

1. На вкладке `Импорт`:
   - инструкция из `--message`;
   - результат последнего импорта;
   - данные выбранного ученика;
   - выбранные номера.

2. На вкладках назначения:
   - статус готовности к верстке;
   - ссылки на рабочие папки;
   - ошибки и предупреждения;
   - детали выбранного фото/ученика/локации.

`--message` показывается только в окне скрипта. В итоговый лог PySM `--message` не выводится.

## Несохраненные изменения

При закрытии окна:

Если есть несохраненный выбор:

```text
Есть несохраненные изменения photo_selection.json.
Сохранить?
[Сохранить] [Не сохранять] [Отмена]
```

Если выбор сохранен, но назначения не пересозданы:

```text
Выбор фотографий изменен, но список назначений photo_assignments.json не пересоздан.
Перейти к верстке пока нельзя.
Закрыть окно?
[Закрыть] [Отмена]
```

Предупреждение не должно жестко блокировать пользователя, но должно явно фиксировать риск.

## Исключаемые папки

Исключаются все папки, указанные в параметре `exclude_dirs`.

`Masks` — только частный пример и текущее значение по умолчанию, а не специальное правило.

Файлы из папок `exclude_dirs`:

- не сканируются;
- не копируются;
- не показываются в таблицах;
- не попадают в HTML/CSV-отчеты.

`CaptureOne` не исключается по умолчанию, потому что для RAW-процесса в ней находятся настройки Capture One.

## Параметры запуска

Единый скрипт должен иметь параметры:

```text
--analysis_dir
--source_dir
--student_list_file
--dest_dir
--exclude_dirs
--title
--message
```

Если текущему `photo_selection` нужны `photo_session` или `session_name`, нужно проверить, можно ли получить их из контекста, `photo_selection.json` или `.list`. Не добавлять лишние CLI-параметры без необходимости.

Параметр `operation` не возвращаем.

## Тесты

Минимальный набор тестов после объединения:

1. Импорт CSV создает/обновляет `photo_selection.json`.
2. Ручное редактирование ученика обновляет `photo_selection.json`.
3. После изменения выбора `photo_assignments.json` считается неактуальным.
4. Повторное открытие готового результата показывает `ГОТОВО К ВЕРСТКЕ`.
5. Устаревший `photo_assignments.json` показывает `НЕ ГОТОВО К ВЕРСТКЕ`.
6. Копирование учитывает все папки из `exclude_dirs`.
7. Файлы из папок `exclude_dirs` не попадают:
   - в таблицы;
   - в HTML;
   - в CSV;
   - в копирование.
8. Вкладка `По ученикам и локациям` показывает отсутствующий выбор.
9. Редактирование номера из вкладки `По ученикам и локациям` обновляет вкладки 2 и 3.
10. `--message` выводится в окне, но не в итоговом логе PySM.
11. `--help` работает.

## Риски

1. Слишком большое окно.
   - Решение: вкладки и две отдельные панели кнопок.

2. Потеря стабильности уже работающего `photo_selection_apply`.
   - Решение: переносить модули постепенно, тесты запускать после каждого этапа.

3. Дублирование моделей `StudentSelection`, `BuildResult`, `PhotoRecord`.
   - Решение: сразу вынести общие модели в один модуль.

4. Неправильная актуальность `photo_assignments.json`.
   - Решение: сравнивать существующий файл с текущим payload, не использовать внутренние флаги доверия.

5. Большой refactor за один шаг.
   - Решение: выполнять этапами и сохранять работоспособность после каждого этапа.
