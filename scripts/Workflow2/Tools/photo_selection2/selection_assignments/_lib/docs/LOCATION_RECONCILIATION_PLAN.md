# План доработки selection_assignments: проверка и исправление локаций

Дата: 2026-10-22.
Статус: реализовано 2026-10-22; результаты проверок — в `../../../_tests/VALIDATION.md`.

## Цель и границы

Перед созданием плана вёрстки проверять соответствие расположения файлов в
`dest_dir` актуальным локациям из `info_faces.json`. По явному нажатию кнопки
перемещать существующие подготовленные файлы в правильные папки, сохраняя ретушь.

- Автоматическая проверка обязательна; новые CLI-параметры не нужны.
- Исправление выполняется только в `selection_assignments` и только внутри `dest_dir`.
- `selection_copy` и `selection_import` не получают новых действий.
- `source_dir` не используется для исправления. Пустой или отсутствующий источник
  не мешает исправлению, если необходимые данные и файлы назначения доступны.
- `info_faces.json` и `photo_selection.json` не редактируются. Формат
  `photo_assignments.json` остаётся прежним: student_id → номера фотографий.
- Существующие изменения объединения записей по номеру и локации сохраняются.
  Отсутствие клиентского выбора в самом генераторе плана — отдельный вопрос;
  этот план не меняет его текущие требования к входным JSON и списку учеников.

## Что обнаружено в текущем коде

- `_common/assignment_core.py::build_assignments()` выдаёт предупреждение
  `location_folder_mismatch`, сравнивая первую подпапку назначения с локацией.
  Файл непосредственно в корне `dest_dir` сейчас не считается несоответствием.
- `has_layout_ready_destination_file()` проверяет расширение, но не правильность
  папки. Наличие JPG/JPEG/PSD в старой локации может считаться достаточным.
- `report_builder.py` определяет актуальность JSON по его содержимому. Поскольку
  локации в JSON не входят, совпадение назначений не подтверждает готовность папок.
- `workers.py` защищает операции от изменения клиентского выбора, но не хранит
  отдельную версию `info_faces.json` для проверки актуальности списка переносов.
- Интерфейс и фоновые операции уже разделены: `assignment_window.py`, `workers.py`,
  `models.py`. Отдельное окно приложения для исправления не требуется.

## 1. Правила сопоставления и целевых путей

1. Проверять все физические файлы в `dest_dir` и его подпапках, соблюдая
   `exclude_dirs` на любой глубине. Не ограничивать проверку текущим выбором
   учеников, списком назначений или файлами с префиксом `PH_`.
2. Использовать существующее извлечение шестизначного номера, включая исключение
   UUID Capture One из разбора имени. Локацию брать именно из анализа, а не из
   резервной записи `unknown`, созданной только из отсутствующего в анализе выбора.
3. Записи анализа одного номера и одинаковой локации объединять независимо от
   остальных частей имени. Разные локации одного номера — блокирующая ошибка:
   автоматически выбрать одну из них нельзя.
4. Стандартная структура: `dest_dir/<локация>/<вложенный путь>/<имя файла>`.
   Для файла во вложенной папке заменять первый компонент пути на актуальную
   локацию, сохраняя остальные компоненты и имя:

   ```text
   dest/group_old/retouch/PH_270015База.psd
       → dest/group_new/retouch/PH_270015База.psd
   ```

   Первая подпапка считается папкой локации даже тогда, когда её имя уже удалено
   из актуального списка локаций. Не вкладывать старую локацию в новую.
5. Файл непосредственно в корне размещать в `dest_dir/<локация>/<имя>`.
   Регистр имён локаций сравнивать без учёта регистра, как сейчас.
6. JPG, PSD, RAW, варианты «База»/«Донор» и сопутствующие файлы с известным номером
   учитывать по отдельности: общий номер определяет локацию, но не делает
   содержимое файлов взаимозаменяемым. Не менять признаки выбора `PH_`.
7. Если в анализе у известного номера локация не задана, сохранять действующее
   правило `unknown`. Файлы с отсутствующим в анализе номером или без номера
   не перемещать; неизвестные номера показывать в предупреждениях.
   Неоднозначные номера не исправлять автоматически и показывать как ошибки.

## 2. Модель проверки и сервис исправления

- Добавить специализированный модуль `_common/location_service.py` с независимыми
  действиями: построение списка несоответствий без записи и применение переносов.
- Описать результат проверки: номер, исходный путь, целевой путь, текущая и
  ожидаемая локации, статус, причина невозможности исправления, версия файла.
- Отдельно возвращать итог выполнения: перенесено, конфликтов, ошибок,
  оставшихся несоответствий. Эти данные передавать через модель состояния и
  результат фоновой операции, без изменения формата пользовательских JSON.
- Проверить общий API `pysm_operations` перед реализацией. Сейчас одиночный перенос
  использует проверку существования цели и `shutil.move`; для этой задачи нужна
  гарантия отказа от замены цели также при её появлении между проверкой и переносом.
  Использовать узкий сервис без перезаписи; не менять поведение общего API ради
  одной операции. Прогресс и оформление отчётов брать из существующих API PySM.

## 3. Автоматическая проверка и блокировка публикации

- Выполнять проверку при открытии окна, по «Обновить список» и непосредственно
  перед сохранением плана. Само сканирование файлов ничего не перемещает.
- Добавить явный пункт готовности «Файлы расположены в актуальных локациях».
- Любое установленное несоответствие у сопоставленного файла назначения
  блокирует создание нового плана, даже если есть другая копия номера в правильной
  папке или этот номер не назначен конкретному ученику.
- Готовым считать JPG/JPEG/PSD назначенного номера в правильной локации.
  Несопоставленные файлы с предупреждениями не превращать в исправляемые файлы.
- Согласовать условия в отчёте, доступности кнопки, worker и функции публикации:
  запрет нельзя обойти прямым вызовом сохранения. Предыдущий JSON сохранять
  без изменения при блокирующих ошибках, но не показывать проект готовым к вёрстке.
- Исправление не должно блокироваться самими исправляемыми несоответствиями:
  отличать их от ошибок входных данных, не позволяющих построить достоверный список.

## 4. Изменения интерфейса

- Сохранить две существующие вкладки и текущий выбор пользователя в таблицах.
- В правой информационной панели добавить список расхождений с номером файла,
  относительными путями «сейчас → должно быть» и статусом конфликта/ошибки.
  Полные пути должны быть доступны для просмотра и открытия существующих файлов.
- Добавить кнопку «Исправить расположение файлов». Она доступна после проверки,
  если есть безопасно выполнимые переносы и не выполняется другая операция.
- Нажатие запускает показанный список переносов. Дополнительные повторяющиеся
  подтверждения для каждого файла не нужны. Если список устарел, обновить его
  и потребовать новое нажатие, не применять незаметно изменившийся набор действий.
- На время работы блокировать конфликтующие действия, показывать этап и прогресс;
  использовать действующий механизм ожидания worker при закрытии окна.
- После завершения перечитать файлы, обновить обе таблицы, отчёт, пути открытия
  и предпросмотр. Показать фактические счётчики и оставшиеся проблемы.
- Исправление не создаёт план автоматически. После успешной проверки пользователь
  отдельно нажимает «Создать план вёрстки».

## 5. Безопасность переноса и конфликты

- Перемещать существующий подготовленный файл; не получать замену из `source_dir`
  и не перекодировать изображение. Создавать необходимые целевые подпапки.
- Проверять принадлежность исходного и целевого путей `dest_dir`, безопасное имя
  локации и отсутствие перехода через символические ссылки/junction за пределы
  проверяемого дерева. Такие пути не обходить для автоматического исправления.
- Составить полный список действий до начала записи. Если две записи претендуют
  на один целевой путь, обе отметить конфликтными; не выбирать победителя по порядку.
- Занятый целевой путь считать конфликтом, даже если занимающий его файл тоже
  запланирован к перемещению. Автоматические обмены путями в первой версии не нужны.
- Не перезаписывать, не переименовывать с суффиксом и не удалять конфликтующие
  файлы, в том числе при совпадении содержимого. Неконфликтующие переносы можно
  выполнить; конфликтующие сохраняются на своих местах и блокируют готовность.
- Перед применением сверять версию `info_faces.json` и актуальность списка путей;
  перед каждым переносом повторно проверять файл и цель. Изменение анализа во время
  операции останавливает дальнейшие переносы и требует новой проверки.
- Использовать перемещение с отказом при существующей цели, включая конкурентное
  появление файла в целевой папке. При заблокированном PSD или отказе доступа
  сохранить источник и показать конкретную ошибку.
- После частичного сбоя не делать слепой обратный перенос успешно перемещённых
  файлов: вывести фактический результат и пересканировать. Повторный запуск должен
  выполнять только оставшиеся действия.
- Пустые старые папки в первой версии не удалять. Если `dest_dir` отсутствует,
  сообщить об отсутствии файлов; автоматической пересортировки выполнять нечего.
- Контроль версии анализа добавить и к созданию плана, а не только к исправлению.
  Существующую защиту от изменения клиентского выбора сохранить.

## 7. Проверки и критерии приёмки

1. Полный сценарий: перенести выбранные PSD в назначение → изменить байты файла
   как имитацию ретуши → изменить локацию в анализе → открыть/обновить план →
   увидеть блокировку → исправить → создать план. Контрольная сумма ретуши сохранена,
   исходная папка пуста, прежний путь отсутствует, правильный путь существует.
2. Объединение двух локаций и разделение одной по разным номерам; повторный запуск
   ничего не перемещает. Проверить корневые файлы и сохранение вложенных путей.
3. Несколько вариантов номера, произвольные имена, PH_ без учёта регистра,
   служебные файлы Capture One с UUID; номера не дублируются в назначениях.
4. Проверить также сопоставленные файлы без PH_ и без выбора учеников.
5. Неизвестные номера, отсутствие номера, неоднозначность, пустая локация,
   конфликт локаций, exclude_dirs, регистр папок и отсутствующий источник.
6. Занятая цель, несколько источников на одну цель, появление цели во время
   операции, отказ доступа, изменение анализа/выбора/файла, частичный сбой,
   symlink/junction и выход за пределы dest_dir: никаких перезаписей и потери ретуши.
7. GUI: автоматическая проверка без записи, кнопка и отображаемый список,
   блокировка создания плана, фоновые операции, закрытие окна во время работы,
   обновлённые пути после исправления. Проверить реальные Qt-действия на временных данных.
8. Регрессия всех трёх этапов: общая тестовая сборка, компиляция, --help,
   JSON паспортов и проверка diff. Реальные фотосессии не изменять без отдельного указания.

## Порядок реализации

1. Модель проверки и тесты расчёта путей без записи.
2. Переносы без перезаписи и тесты конфликтов/частичных ошибок.
3. Единая проверка готовности и запрет публикации с неверными локациями.
4. Фоновая операция, кнопка и отчёт, защита от устаревших данных.
5. Полный пользовательский сценарий, регрессии, руководство и журнал изменений.

Готовность: после изменения локаций пользователь может исправить расположение
подготовленных файлов из окна плана и успешно сформировать назначения; все
неустранённые конфликты видны и исключают ложный статус готовности.
