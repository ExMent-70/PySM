# RMBG Process

Скрипт отделяет рабочие пути от настроек качества:

- `config_var` указывает на JSON-профиль, созданный `RMBG Configurator`;
- `input_dir`, `output_dir` и `background_dir` передаются при запуске;
- `model_dir` хранится в секции `model` JSON-профиля относительно корня PySM и настраивается через Configurator;
- `recursive`, `overwrite`, `dry_run` и `fail_fast` относятся только к текущему запуску.

## Первый запуск

1. Сохраните профиль через Configurator.
2. Укажите папки `input_dir` и `output_dir`.
   Если профиль создаёт composite на изображении, передайте `background_dir`,
   содержащий выбранный в Configurator файл по тому же относительному пути.
3. Для первого запуска включите `dry_run`.
4. Проверьте выбранную модель, её статус, разрешение, количество найденных изображений и upstream commit.
5. Отключите `dry_run` и запустите обработку.

`dry_run` не создаёт выходную папку, не загружает модели и не изменяет изображения.

## Профиль и эффективная модель

Название профиля используется как подпись в конфигурации и отчёте и само по себе не влияет на обработку. Если модель выбрана автоматически, Process применяет соответствие: `Универсальный HQ` → `RMBG-2.0`, `Портрет и волосы HQ` → `BiRefNet-portrait`, `Прозрачные объекты HQ` → `Lucida`, `Пользовательский` → `BiRefNet-general`.

Конкретная модель, выбранная вручную, всегда имеет приоритет над типом изображений. Эффективная модель записывается в `pipeline.model_id` итогового manifest.

## Автоматическое скачивание моделей

При обычном запуске Process сначала разрешает `model.model_dir` относительно корня текущей установки PySM и проверяет выбранную модель. Например, `_BIN/models/RMBG` превращается в фактический каталог `<корень PySM>/_BIN/models/RMBG`. Выход относительного пути за пределы корня PySM запрещён. Если одного или нескольких файлов нет, они автоматически скачиваются из зафиксированного Hugging Face repository. Пользователю не требуется заранее создавать подпапки или вручную копировать веса. Отдельного CLI-параметра `--model_dir` у Process нет: путь настраивается один раз и затем одинаково используется Configurator, тестовой генерацией и пакетной обработкой.

Для каждого файла показывается отдельный progress bar `Загрузка модели: <имя файла>`. Небольшие конфигурации считаются в байтах, веса — в MiB. После завершения загрузки появляется обычный progress bar обработки изображений.

Безопасность загрузки:

- repository, точный revision, размер и SHA-256 каждого файла зафиксированы в `models.lock.json`;
- данные сначала записываются в уникальный временный файл рядом с целевым;
- конечное имя публикуется атомарно только после проверки размера и SHA-256;
- временный файл удаляется при сетевой ошибке или несовпадении checksum;
- существующий повреждённый или неизвестный файл автоматически не перезаписывается;
- `dry_run` никогда не обращается к сети и ничего не скачивает.

Нужен доступ к `huggingface.co`. Автоматическая production-загрузка активна для `RMBG-2.0`, `Lucida` и всех десяти подключённых вариантов семейства BiRefNet. При выборе SDMatte тем же безопасным способом загружаются его checkpoint и необходимые конфигурации; зафиксированный Python-runtime скачивается с конкретного upstream commit и также проверяется по SHA-256.

## Поддерживаемые production-модели

Все модели имеют статус `verified` после реальной CUDA/FP16-проверки на трёх изображениях. Для HR и 2K-вариантов использовалось штатное разрешение 2048, для `BiRefNet_512x512` — 512, для остальных — 1024.

- `RMBG-2.0` — универсальная модель; хорошо сохраняет объект вместе с функционально связанным реквизитом и опорами;
- `BiRefNet-general` — сбалансированный универсальный вариант для людей и предметов;
- `BiRefNet_512x512` — компактный вариант с рекомендуемым разрешением 512;
- `BiRefNet-HR` — высокое разрешение для мелких деталей и сложных краёв;
- `BiRefNet-portrait` — основной выбор для портретов, волос и сложных контуров человека;
- `BiRefNet-matting` — мягкие и полупрозрачные границы общего назначения;
- `BiRefNet-HR-matting` — высокодетальный matting при 2048;
- `BiRefNet_lite` — облегчённая универсальная архитектура;
- `BiRefNet_lite-2K` — облегчённая архитектура для высокого разрешения;
- `BiRefNet_dynamic` — динамический DIS-профиль для разных типов объектов;
- `BiRefNet_lite-matting` — облегчённый matting-профиль;
- `Lucida` — специализированный вариант для прозрачности, свечения, текста и иллюстративных объектов; на обычной фотографии может сохранять больше элементов переднего плана.

`RMBG-2.0` хранит веса в FP32 и выполняет CUDA-операции через FP16 autocast. Это устраняет несовместимость внутренних Float/Half-тензоров, сохраняя ускоренное вычисление. Для остальных моделей применяется прямой FP16 runtime. Lite-варианты загружают отдельный зафиксированный source-файл `birefnet_lite.py`; он не переименовывается и также проверяется по SHA-256.

Контракт разрешений:

| Модель | По умолчанию | Допустимый диапазон |
|---|---:|---:|
| BiRefNet-general, portrait, matting, lite, dynamic, lite-matting | 1024 | 512–2048 |
| BiRefNet_512x512 | 512 | 256–1024 |
| BiRefNet-HR, HR-matting, lite-2K | 2048 | 1024–2560 |

`process_resolution=0` означает штатное значение выбранной модели. Явное значение вне её диапазона отклоняется до загрузки весов.

По умолчанию поле `model.model_dir` указывает на `_BIN/models/RMBG`: `RMBG-2.0` хранится в подкаталоге `RMBG-2.0`, а семейство BiRefNet и Lucida — в `BiRefNet`. Перед запуском проверяются SHA-256 весов, конфигурации и Python-кода модели.

Inference автоматически выполняется последовательно по одному изображению: CUDA-замеры BiRefNet показали, что `batch_size=1` даёт максимальную пропускную способность и минимальный расход VRAM. Batch 2 и 4 на проверенной GPU оказались медленнее и увеличили пиковую память примерно с 1,6 до 2,8 и 5,1 ГБ. Эта техническая настройка больше не показывается в Configurator.

CPU-постобработка и запись результатов работают конвейерно: пока GPU строит следующую маску, предыдущие изображения параллельно обрабатываются и сохраняются через `io_workers`. Чтение следующего JPEG выполняется с ограниченным prefetch. Рекомендуемое значение `io_workers=4`; для очень больших файлов или небольшого объёма RAM используйте 2, для многоядерного CPU допустимы 6–8.

PNG сохраняется без потери качества с `png_compress_level=3`. По контрольному замеру этот уровень примерно вдвое быстрее стандартного уровня 6 для RGBA cutout, а файл получается приблизительно на 8% больше. Значения пикселей и 16-битная точность маски не меняются. Уровень 6 можно выбрать, если размер файлов важнее скорости.

Итоговые изображения можно сохранять в PNG, lossless WebP или JPEG. Для JPEG доступно качество `1–100`, рекомендуемое значение — `95`; используется качественная цветовая дискретизация 4:4:4. JPEG не поддерживает alpha: cutout накладывается на выбранный сплошной цвет, а composite сохраняется как обычное RGB-изображение. Полутоновая маска независимо от выбранного формата всегда остаётся 16-битным PNG.

Если включён `fail_fast`, CPU/I/O pipeline намеренно переключается на один поток, чтобы обработка остановилась строго на первом ошибочном изображении. Устаревшие поля schema v1 `batch_size`, `max_loaded_models` и `allow_cpu_fallback` сохраняются только для чтения старых профилей и автоматически нормализуются в фактический контракт: batch 1, одна основная модель и отсутствие неработающего CPU fallback.

## Прогресс обработки

Во время обычного запуска PySM показывает штатный progress bar. До первого изображения он сообщает о загрузке модели, затем отображает имя текущего файла и три счётчика: обработано, пропущено и ошибок. Готовые файлы тоже учитываются в общем прогрессе, поэтому полоса всегда соответствует количеству найденных исходников. После завершения или ошибки progress bar закрывается и сбрасывается.

Перед загрузкой модели консоль показывает основные настройки создания маски: модель и разрешение, refinement, чувствительность, размытие, смещение края, растушёвку, заполнение отверстий, удаление мелких областей, инверсию и количество найденных изображений. В PySM сводка оформляется как HTML-блок: заголовок не содержит служебных символов, а названия параметров выделены жирным шрифтом. В `dry_run` после этой сводки выводится только подтверждение успешной проверки.

После обработки сначала выводится таблица «Папки и отчёт RMBG», а непосредственно под ней — компактный итог без отдельного заголовка: статус, количество найденных, обработанных, пропущенных и ошибочных файлов, а также общее время. Названия показателей выделены жирным шрифтом. Полное содержимое `manifest.json` в консоль не печатается.

Таблица содержит кликабельную ссылку на папку исходных изображений, отдельную ссылку для каждого включённого типа результата и ссылку на `Reports/manifest.json`. Например, если включено сохранение итоговых изображений и полутоновой маски, показываются отдельные папки `Cutout` и `Masks`; если включён composite, дополнительно появляется папка `Composite`. Отключённые типы результата в таблицу не добавляются. События progress bar по-прежнему передаются через `stderr` в служебном протоколе PySM.

## Результаты

В зависимости от профиля создаются:

- `Cutout` — PNG или lossless WebP с непремультиплированным alpha либо JPEG на выбранном сплошном цвете;
- `Masks` — полутоновая 16-bit PNG-маска;
- `Composite` — PNG, lossless WebP или JPEG с объектом на сплошном цвете либо выбранном фоновом изображении;
- `Reports/manifest.json` — атомарно обновляемый отчёт с config hash, upstream commit, временем, статусом и путями каждого файла. Во время длинного запуска checkpoint записывается не чаще одного раза в две секунды и обязательно обновляется при ошибке и завершении.

В manifest отдельно записываются `model_load_seconds`, `processing_seconds` и `throughput_images_per_second`. Поэтому скорость обработки можно оценивать без времени первичной загрузки Python-модулей и весов. Для SDMatte также фиксируются variant, разрешение, режим прозрачности, constraint, repository/revision, checkpoint с checksum и файлы, скачанные именно в этом запуске.

### Контракт фонового изображения

`background_dir` — runtime-папка, а не часть профиля. В профиле хранится только относительный путь файла, выбранного через RMBG Configurator. Process безопасно разрешает этот путь внутри переданного `background_dir` и останавливается с понятной ошибкой, если папка, выбор или файл отсутствует. Выход за пределы папки запрещён.

Один выбранный файл применяется ко всем исходным изображениям текущего запуска. Старое автоматическое сопоставление нескольких фонов по относительному пути или имени без расширения удалено.

Фон подгоняется к размеру каждого исходника одним из способов:

- `cover` — сохраняет пропорции, полностью заполняет кадр и обрезает лишнее в выбранной позиции: центр, верх, низ, лево или право;
- `contain` — сохраняет пропорции, показывает фон целиком и заполняет свободные поля цветом из профиля;
- `stretch` — растягивает фон точно до размера исходника.

Масштабирование во всех режимах выполняется с Lanczos. `cover` с положением по центру используется по умолчанию.

Вложенная структура `input_dir` сохраняется. Если все ожидаемые результаты уже существуют и `overwrite=false`, изображение пропускается. Неполный набор блокируется: это не позволяет смешать артефакты разных запусков. `output_dir` нельзя размещать внутри `input_dir`.

### Уточнение маски

Эффективный порядок обработки: нормализация исходной маски → выбранный refinement → sensitivity → blur → offset → удаление мелких областей → заполнение отверстий → feather → invert. Каждый параметр применяется ровно один раз.

- `auto` в текущей версии разрешается в `fast`;
- `none` пропускает дополнительное уточнение;
- `fast` выполняет быстрый CPU-алгоритм без отдельной модели;
- `sdmatte` использует исходное изображение и маску основной модели как visual prompt для HQ alpha matte.

SDMatte проверяет наличие `diffusers`, `accelerate` и CUDA до скачивания весов. Зафиксированный runtime ComfyUI-RMBG 3.1.0 является CUDA-only; CPU fallback для него намеренно не выполняется. Один checkpoint занимает около 5,19 ГБ. Рекомендуемое разрешение — 1024. В реальном QA-прогоне `BiRefNet-portrait + SDMatte` при 1024 обработал три изображения без ошибок; пиковое выделение CUDA-памяти составило 8,74 ГиБ на RTX 4070 Ti SUPER 16GB, а полная обработка одного кадра после загрузки моделей занимала примерно 1,8–2,6 секунды.

В текущем процессе удаления фона SDMatte получает маску непосредственно из памяти после выбранной основной RMBG-модели. Промежуточная маска не сохраняется и не читается повторно. Отдельный CLI-параметр входных масок появится только вместе с будущим самостоятельным режимом уточнения внешних масок.

После обработки модель всегда явно выгружается и CUDA-кеш очищается. Поле схемы `unload_after_run` сохраняется только для совместимости с ранее записанными профилями; значение `false` нормализуется в безопасное `true`.

## Коды завершения

- `0` — dry-run или обработка успешно выполнены;
- `2` — ошибка конфигурации, контекста или входных путей;
- `3` — выбранный inference-адаптер отсутствует или ещё не имеет статуса `verified`;
- `4` — ошибка загрузки/обработки или один из файлов завершился ошибкой.
